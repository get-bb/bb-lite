Everything is a plugin

A proposal for rewriting bb-150k's plugin API so that the product itself is built from the same plugins third parties write. Draft for discussion, 8 October 2026.

The proposal in one paragraph. Shrink bb to a small kernel that knows how to do four things: load plugins, let a plugin define typed operations that anyone can call and anyone can wrap, let a plugin define slots that other plugins fill, and hand each plugin its own storage. Because every action passes through it, the kernel also records who did what and through which plugin. Threads, providers, environments, sign-in, the sidebar, the composer and every CLI command then become plugins written against that one public API. A plugin stops being "a server file and an app file" and becomes a package with a part for each place bb runs code: the server, the machine runner and the browser.

Seven ideas carry the design. Each is taken from one of the systems you asked me to study.

IdeaWhat it means for bbTaken from
One hook shapeEvery operation can be wrapped with (e, next). The plugin that owns the operation is the last link in the chain, so core behaviour and plugin behaviour are the same kind of thing.Claude Code mods; DeepSeek Harness "waterfall" events
Plugins define the extension pointsThe kernel has no list of slots. The shell plugin defines the shell's slots, the thread view defines its own, and Tasks can define slots inside Tasks.DeepSeek Harness ("declaring a slot is claiming it")
A part per runtimeA plugin can have a server part, a browser part and a part that runs on each machine. That last one is what lets providers and environments be plugins.Original bb (server, app, host); Pi's experimental facets
One operation, several doorsDefine "create a task" once; the kernel offers it to the app, the CLI, agents and HTTP.DeepSeek Harness; bb's own CLI dispatch
The product is a listA build of bb is a profile: a named list of plugins. The default profile is today's product.DeepSeek Harness profiles; Hermes backend selection
Every action has an authorEach operation carries who started it and which plugins it passed through, and the kernel records it. With several people and several plugins in one workspace, "who did this, through what?" always has an answer.bb's own actor model; Claude Code's next.origin
Everything registered can be undoneThe loader records every registration and reverses it on unload or failed load, which is what makes reload-on-save safe.Hermes's ledger; DeepSeek Harness effects; original bb's reload

Three things I would deliberately leave out for now: a sandbox for plugin code, a way to draw the same plugin UI on surfaces other than the web app, and any promise that the thread engine can be swapped for another one. Sections 14 and 15 say why and what you would be deciding.

Sections 1 to 3 are findings. Sections 4 to 12 are the proposal. Sections 13 to 15 are how to get there and the choices that are yours.

1Where bb-150k was before this work

A plugin is a directory with a bb block in package.json, a server.ts that receives a bb object, and an app.tsx that registers into slots. Eight plugins ship in the repository. Together they are about 19,000 lines; the server, runner and app that are not plugins are about 92,000.

The parts worth keeping: one factory function per side, typed RPC between a plugin's two halves, a SQLite file per plugin, CLI commands that run on the server so the CLI needs no plugin code, and the rule that a failing plugin never stops the server.

The signs that plugins are second class:

SignEvidence
Plugins can listen but not intervenePluginEvents has eight events, all after the fact. To get anything from plugins, the thread engine asks the plugin host eight fixed questions (instructionsFor, toolsFor, callTool, contributedEnv, emit, searchMentions, generateTitle, skillDirs). A ninth need is a change to core.
No plugin code runs on a machineProviders are a closed type ("codex" | "claude-code" | "echo" in packages/runner/src/types.ts) and environment kinds are a closed enum. A remote runner never loads plugin code.
Core defines every slot, and the biggest areas have noneNine app slots. Timeline rows, tool-call details, composer controls, pickers, thread actions, right-panel tab kinds, settings sections and the navigation rail are inline switches.
APIs that exist for one pluginmachines.setAccessProvider and server.tunnelToken (connect), useQuestionFormHost (ask-user-question), ten useSidebar… hooks (thread-list).
The bundled plugins could not be written by a third partyTheir UIs import @bb/shared-ui and @bb/client-core, which are not among the 15 modules shared with external plugins. They work because they are compiled into the app.
Seams that lead nowhereenvironments.register and mention resolution are accepted by the API and nothing in the server reads them.
The shared schemas are closed listsEvent types, timeline row kinds, tab kinds, change kinds and command ids are exhaustive zod unions that the app, SDK, CLI and Rust crates all switch on.
No dependencies, scopes or reload on saveA plugin cannot require or extend another plugin. Settings and storage have one scope for the whole server. Reload is a manual command.

The original bb has a far larger API (24 app slots, a host tier on every machine, providers and environments as plugins), and bb-150k pared that back on purpose. Both share one model, though: core decides what can be extended, one surface at a time. The original shows where that model goes when it grows, which is the first lesson in the next section.

2What the references teach

I found all five. Each was read from source: the four outside projects from fresh clones, the original bb from ~/projects/bb (read only). For each, the idea worth taking and the mistake worth avoiding.

Original bb

@get-bb/plugin-sdk 0.6.28 · commit 32f63ea · about 40 bundled plugins

The closest thing to the goal that already exists. Providers, environments, the sidebar, memory, workflows and remote access are all plugins. A plugin has three tiers: a server factory, a browser bundle and a host part that the daemon on each machine runs in its own process.

Take:

  • The host tier. It is the only reason providers and environments can be plugins there.
  • Reload builds the new registrations first and keeps the old plugin running if that fails.
  • Replacement slots (thread list, diff renderer) with a user preference and a built-in fallback.
  • Skills, CLI commands, tools and instructions as things a plugin gives to agents.

Avoid:

  • Growth by one-off. 24 app.slots.* methods plus five sibling registries; commands can be registered three ways; over 100 identifiers still prefixed experimental_; the app contract alone is 3,743 lines.
  • Exactly one hook (message.dispatch). Everything else is an event after the fact, so new behaviour needs a core change.
  • Core still names plugins: side-chat, thread-list and onboarding are special-cased by id.

Claude Code mods

Claude Code v2.1.287+ · read from the docs and the bundled reference

The cleanest model of the five. A mod registers on(event, matcher, ($, e, next) => …). next(e) runs the mods beneath and then Claude Code's own behaviour, so a hook can watch, rewrite or answer.

Take:

  • One hook shape for everything, including drawing (ui.render per site) and the API itself (every $ method is also an event another mod can intercept).
  • Built-in features are mods: /diff, AGENTS.md loading, telemetry and the security guard.
  • A mod can add a namespace to the API and ship its types as a contract that dependants receive.
  • validate lists hooks and calls without running the code; test runs against the real engine.
  • State the host holds survives a hot reload; module variables do not.

Avoid:

  • The price of full generality. The type reference is about 14,000 lines, with rules for re-entry, time budgets and text limits that an author must learn.
  • An element system per surface (terminal, desktop, mobile) is a product in itself.

Pi

badlogic/pi-mono, now earendil-works/pi · commit 1cedd32

A deliberately small core with a large extension API: pi.on(event, handler) plus registerTool, registerCommand, registerProvider and a ctx.ui for dialogs and widgets. Sub-agents, plan mode and permission gates are left out of core and shipped as example extensions.

Take:

  • Each event declares what a handler may do: tool_call may block, input may transform or handle, most only notify.
  • Built-ins as replaceable extensions: MCP, tool search and code mode are marked replaceable, and a third-party extension that registers the same names takes their place.
  • Dialogs, status and widgets are a small serializable protocol, so they work in the terminal and over RPC.
  • The experimental "chord" plugins: per-environment facets, typed service contracts, replicated state.

Avoid:

  • Rich UI returns terminal components, so no other client can show it.
  • A different conflict rule per surface: tools are first-wins, shortcuts last-wins, commands get a numeric suffix.
  • No API version in the manifest, and tools cannot be unregistered.

Hermes Agent

NousResearch/hermes-agent · commit 61b7f95 · 103 bundled plugin.yaml

A Python agent with a plugin.yaml manifest and a register(ctx) function. Model providers, chat platforms, search, image, speech and memory backends are plugins. The agent loop and the built-in tools are not.

Take:

  • An ownership ledger: every registration returns a handle, and unload, failed load and timeout all roll back through it and restore what was displaced.
  • A table of provider categories: one row gives a category its interface, its registry and the config key that picks the active one.
  • Failure policy per hook, and an activation summary after reload.
  • Process isolation as a config switch (plugins.isolation: host) with unchanged plugin code.

Avoid:

  • Four discovery systems with opposite rules for who wins a name.
  • Product features leaking into the generic API: register_telegram_handler, eight kanban hooks.
  • Core not using its own API: 47 built-in tool files register directly, bypassing the plugin context.
  • Three unrelated UI plugin mechanisms (dashboard, TUI, desktop).

DeepSeek Harness

deepseek-ai/deepseek-harness · commit 5badb15 · v0.2.1-alpha.1

The one that really is plugins all the way down. It is built on Cordis, a small dependency-injection kernel. The model client, sessions, the tool registry, the agent loop and the plugin manager itself are rows in a YAML list, and the whole web UI is some 60 browser plugins.

Take:

  • Plugins declare the services they need (inject); there is no load order to maintain.
  • Every registration is a reversible effect, so unload and hot reload come for free.
  • UI slots that plugins declare, with kinds (single, list, keyed, chain); registering into an undeclared slot is a load error.
  • Profiles, and --dump-config to show which layer set each row.
  • Creator mode: the agent gets tools to inspect the live services, events and slots, then writes and installs a plugin.
  • The rule that a UI action and an agent tool share one host method.

Avoid:

  • The authoring weight: 319 packages, types extended by declaration merging everywhere.
  • Replacing a default is "disable its row, insert yours" by convention, with no check that the replacement fits.
  • A list of required plugin ids hard-coded in the launcher, which undercuts "no privileged core".

Two patterns stand out. The systems where core uses its own API (DeepSeek, and Claude Code for some features) have one general mechanism. 3How bb differs from them

All four outside references are harnesses: each owns the loop that sends a request to a model, runs the tool it asks for, and sends the result back. bb sits one level up. It runs other people's harnesses (Claude Code, Codex) on machines, and owns the threads, queues, workspaces, people and screen around them. That changes the design in three ways.

  1. The moments worth hooking are different. bb does not see every Bash call before it runs. It sees what a provider reports: turns, items, approval requests, calls to bb's own tools. So bb's hooks sit at sending a message, deciding whether to queue it, building the session a provider starts from, an approval request arriving, events being stored, and a thread changing state.
  2. There are more places code runs. A harness is one process with one screen. bb has a server, a runner on each machine, a browser per person, and several people. A plugin API for bb has to say where each piece of a plugin runs and how the pieces talk. Of the references, only Pi's experimental "chord" plugins and Hermes's dashboard plugins face this at all.
  3. bb can carry harness plugins down with it. A bb plugin already ships skills into every session. The same route can ship a Claude Code mod or a Pi extension. "Stop rm -rf inside Claude Code" is a mod that a bb plugin delivers; "show that question in the bb app and let a teammate answer it" is a bb hook. The two layers complement each other, and bb should not try to rebuild the lower one.

4The kernel: what is left when everything is a plugin

The kernel is the part of bb that is not a plugin. It should be small enough to read in an afternoon, and it should not know what a thread, a provider or a sidebar is. It has seven parts. A plugin author sees the first four; the last three work underneath every call.

Kernel partWhat it doesNearest code today
LoaderReads manifests, works out which plugins need which, bundles each plugin's parts, starts them in dependency order, and undoes everything a plugin registered when it unloads or fails to load.apps/server/src/plugins/, apps/app/src/plugins/
OperationsLets a plugin define, implement, call and wrap typed functions, and carries a call from one runtime to another.plugin RPC, the typed routes in server-contract, the runner protocol
SlotsLets a plugin define a typed list and lets others add to it, wrap an entry or replace it.apps/app/src/plugins/registry.ts

AuditRecords every operation that changes something: who started it, which plugins it passed through, which hook changed or refused it, and how it ended. It lives in the kernel so that no plugin can skip it.actorUserId on turn requests, created_by_user_id on threads

5Three primitives

Today's server API has 22 namespaces and the app API has 9 slots and about 20 hooks, and each was built by hand in core for a particular need. The proposal replaces them with three things a plugin can define, and a handful of verbs for using what other plugins defined.

The contract: what a plugin offers, as types

Each plugin has a contract: a file of names and schemas with no behaviour in it. Other plugins import the contract, never the implementation. Because it is only types and zod schemas, it is safe to import from the server, the runner and the browser alike.

// plugins/threads/contract.ts
import { contract, op, event } from "@bb/plugin";

export const threads = contract("threads", {
  send:   op({ input: SendInput, output: SendResult, allow: "member" }),
  stop:   op({ input: ThreadRef, output: Nothing,   allow: "member" }),
  title:  op({ input: TitleInput, output: Title }),
  idle:   event({ thread: Thread, lastAssistantText: Text.nullable() }),
});

Primitive 1: operations

An operation is a named, typed function. One plugin implements it. Any plugin can call it. Any plugin can wrap it with a hook, and the implementation is simply the last link in the chain of hooks. This is the shape Claude Code mods use (($, e, next)), and it lets one mechanism cover three needs that today have three separate APIs.

// the owner: plugins/threads/server.ts
export default plugin((bb) => {
  bb.implement(threads.send, (input, ctx) => engine.send(input, ctx.caller));
});

// call it: any other plugin, in any runtime
await bb.call(threads.send, { threadId, text: "Run the tests again" });

// observe it: let it through, then act on the result
bb.on(threads.send, async (e, next) => {
  const result = await next(e);
  metrics.count("sent");
  return result;
});

// rewrite it: change what the rest of the chain sees
bb.on(threads.title, async (e, next) => next({ ...e, maxLength: 48 }));

// answer it: do not call next, so the owner never runs
bb.on(threads.title, { projectId: "proj_personal" }, async () => ({ title: "Scratch" }));

An event is the simple case: an operation with nobody to answer it. bb.emit(threads.idle, …) tells whoever is listening; bb.on(threads.idle, …) listens.

The contract states what a hook may do with each operation: only watch, change the input, or answer in the owner's place. Pi does this per event (its tool_call handlers may block, its input handlers may transform or handle) and it keeps hooks honest: a plugin cannot quietly swallow threads.send unless the threads plugin said that is allowed.

One operation, several doors

Today the tasks plugin describes "create a task" once as an RPC method for its app half, again as a CLI command, and again for agents. An operation can say where it should be reachable, and the kernel builds each door from the one schema.

export const tasks = contract("tasks", {
  create: op({
    input: z.object({ title: z.string(), project: z.string().optional() }),
    output: Task,
    allow: "member",
    doors: {
      cli: "tasks create <title> [--project <key>]",   // bb tasks create …
      agent: "Create a task in bb Tasks",               // a tool in every session
      http: "POST /tasks",                              // for scripts and webhooks
    },                                                  // the app can always call it
  }),
});

This is also what makes the CLI a plugin surface with no plugin code in it: the Rust and Node CLIs already ask the server for plugin commands and send argv to it. With doors, every bb command except bb server and bb runner can come from that table.

Primitive 2: slots

A slot is a named, typed list that one plugin defines and reads, and other plugins add to. Slots are for things that are collections by nature: providers, kinds of environment, navigation panels, renderers for timeline rows, settings pages, commands.

// plugins/shell/contract.ts
export const shell = contract("shell", {
  navPanel:   slot({ item: NavPanel }),
  command:    slot({ item: Command }),
  threadList: slot({ item: ThreadListView, pick: "one" }),   // exactly one is active
});

// plugins/tasks/app.tsx
bb.add(shell.navPanel, { id: "tasks", title: "Tasks", icon: "Tasks", path: "/tasks", view: TasksApp });

// plugins/sessions/contract.ts, filled on the runner
export const sessions = contract("sessions", {
  provider: slot({ item: ProviderAdapter, key: "id" }),
});

// plugins/provider-codex/runner.ts
bb.add(sessions.provider, codexAdapter);

The important change is who defines them. Today all nine app slots are defined by core, so adding a tenth means changing core. Here the shell plugin defines the shell's slots, the thread view defines its own, and the tasks plugin can define tasks.detailSection so that someone else can extend Tasks. A plugin's own surface is extendable by the same means as bb's.

pick: "one" covers the "choose a backend" case that Hermes handles with a config key per category (memory.provider, tts.provider): several plugins may add an entry, one is active, and the choice is a setting. When the active one unloads, the one it displaced comes back.

Primitive 3: state

const db = bb.db({ migrations });                 // this plugin's own SQLite file
const kv = bb.kv;                                 // small values, no schema
const settings = bb.settings.define(fields, { scope: "user" });   // workspace | user | project
const unread = bb.live("unread", 0);              // held by the server, pushed to subscribers

bb.live replaces realtime.publish plus hand-written cache invalidation: the server holds the value, the app reads it with useLive(tasks.unread), and it survives a reload of the plugin because the kernel holds it, not the plugin's module. Claude mods separate $.state (the host's, survives reload) from module variables (lost on reload) for the same reason. Settings take a scope from the start, because bb is multi-user now and the current API has one scope for the whole server.

6One plugin, several runtimes

A plugin today is a server file and an app file. That is why providers and environments cannot be plugins: both run on the machine, inside the runner, and a plugin has no part there. The proposal gives a plugin up to three code parts, each with the same bb verbs.

app.tsxBrowser, one per person.
Fills screen slots, calls operations, reads live values.
server.tsServer, one per workspace.
Implements operations, owns the database, hooks the product core.
runner.tsRunner, one per machine.
Provider adapters, environment kinds, anything that touches the machine's files and processes.
No code: doorsCLI, agent tools, HTTP.
Built by the kernel from operations that ask for them.
// plugins/provider-codex/package.json
"bb": {
  "id": "provider-codex",
  "name": "Codex",
  "requires": ["sessions"],
  "contract": "./contract.ts",
  "server": "./server.ts",
  "runner": "./runner.ts",
  "app": "./app.tsx",
  "skills": "./skills"
}

Two rules keep this simple:

  • Operations cross runtimes; slots do not. The app calls a server operation, the server calls a runner operation, and the kernel carries the call (over HTTP and the WebSocket for the app, over the existing runner link for machines). A slot lives in one runtime. When another runtime needs to know what is in it, the owner offers an operation: the sessions plugin answers sessions.providers so the app can draw a model picker.
  • The server hands out the code. It already bundles a plugin's app part and serves it to browsers. It would bundle the runner part the same way and send it down the runner link when a machine connects, keyed by content hash, so a remote machine never needs the plugin installed by hand.

The runner protocol does not need to change shape. It is already "call a named method, get a result, receive events on a reliable lane"; the method names become operation names, and the rule "only the methods of Runner can be called" becomes "only operations a runner part implements". ProviderAdapter (status, listModels, open) is already the right shape for a slot entry.

Precedent. The original bb already has this third part: a plugin's host entry runs in the daemon on each machine, and that is how its Claude Code, Codex and worktree plugins work. bb-150k dropped it when it folded the daemon into the runner. Pi is trying the same split in its experimental "chord" plugins: a plugin declares facets (a session worker and a TUI), they share a typed service contract, and the server builds the UI facet and ships it to clients. Hermes went the other way and ended up with three unrelated UI plugin mechanisms (dashboard, TUI, desktop) that share nothing.

7The app is plugins too

"Everything is a plugin" is hardest in the app, because a screen is a tree and somebody has to own each level. The proposal: a few screen plugins each own one region and define the slots inside it.

PluginOwnsSlots it defines for others

thread-viewThe timeline and the thread headerrow (one renderer per kind of row), panel, headerAction, directive, interaction

A plugin can do three things to a slot, and these are the whole UI extension model:

  • Add an entry: a panel, a command, a renderer for a new kind of row.
  • Wrap an entry someone else added: bb.wrap(threadView.row, { kind: "tool-call" }, (Row) => (props) => …). This is the React form of a hook, the same idea as a Claude mod answering ui.render for the ToolUse site and calling next.
  • Replace the active entry of a pick-one slot: a different sidebar, a different thread list.

What an app part looks like

Prefer data to components

Commands, menu items, badges, status lines, toasts, settings forms and questions to the user can all be described as plain data. Data contributions cost nothing to render somewhere new: the same command shows up in the web command palette, in bb help, and in a phone layout. Components are for when a plugin needs its own pixels.

The references show both sides of this. Pi's dialogs, status and widgets are a small serializable protocol, so they work in its terminal UI and over RPC; its custom renderers return terminal components, so they reach no other client. Claude mods solved it with an element table per surface, which is powerful and a large thing to build. For bb I would not build a cross-surface element system now. I would make the data contributions rich and let React cover the rest.

What the app half stops needing

The app API today exports hooks that exist because one plugin needed core's private state: useSidebarThreads, useSidebarThreadDraft, useQuestionFormHost and so on. When the thread engine publishes a contract, those become useOp(threads.list, …) and useLive(…) against it, and the app API shrinks to a few generic hooks plus shared components such as ThreadChat, which the thread-view plugin would export through its contract.

The four hard parts

The table makes this look like a matter of moving files. Four things are harder than that.

  1. Closed lists have to open. Event types, row kinds, tab kinds, change kinds and command ids are exhaustive unions that five packages switch on, the Rust CLI among them. Each becomes "a common envelope, plus a payload checked by whichever plugin registered that kind", and every consumer needs a default for kinds it does not know.
  2. One database with joins. The thread list joins threads, events, environments, machines and per-user state. Plugins today get a separate SQLite file each, which cannot join. I would let a plugin ask for tables in the shared database, with migrations ordered by requires, and let a contract publish a table or view that others may read. Writes stay with the owner. This is the design question I am least sure of.
  3. The typed HTTP contract and SDK assume a fixed set of routes. public-api.ts is one file of 1,000 lines and the SDK mirrors it by area. Both become compositions of plugin contracts.
  4. App parts need far more shared code than 15 modules. The query client, the router, the UI kit and other plugins' contracts all have to be importable by an external plugin, or first-party plugins keep an advantage that third parties cannot have.

The same plugin, before and after

Custom instructions is the smallest real plugin in the repository. Before, it uses three purpose-built APIs (settings, contributeInstructions, a hand-built CLI). After, it is one hook and two operations.

// plugins/custom-instructions/server.ts, proposed
import { plugin } from "@bb/plugin";
import { sessions } from "@bb/sessions/contract";
import { customInstructions as own } from "./contract";

export default plugin((bb) => {
  const settings = bb.settings.define({
    text: { type: "string", multiline: true, default: "", label: "Custom instructions" },
  });

  bb.on(sessions.instructions, async (e, next) => {
    const sections = await next(e);
    const { text } = await settings.get();
    return text.trim() ? [...sections, { id: "custom", text }] : sections;
  });

  bb.implement(own.get, async () => (await settings.get()).text);      // door: bb instructions get
  bb.implement(own.set, async ({ text }) => { await settings.set({ text }); });   // door: bb instructions set
});

11Trust, audit, order and failure

Trust

Plugin code would run in the server process, the runner process and the page with full authority, as it does today. Every reference does the same: Claude's docs say "a mod is code that runs with your permissions", DeepSeek's say its checks are "not a sandbox against malicious package code", and Pi has no permission model. Only Hermes offers a separate process, as an opt-in. I would not build a sandbox now, but I would build three cheaper things:

  • Who may call. Each operation states who may call it (owner, member, runner, anyone) and the kernel checks it. The identity plugin decides who the caller is; the kernel only enforces. Today that check is spread across the trust middleware and individual routes.
  • What it touches, before it runs. Because a plugin reaches the rest of bb only through bb.call, bb.on and bb.add on named contracts, bb plugin validate can list what a plugin hooks and calls by reading its source, and installing can show that list. Claude Code does this (claude plugin validate prints hooks: and calls:). It does not stop a plugin from using node:fs directly, so it is a description for the installer, not a guarantee.
  • Who may install what. Server and runner parts are installed by a workspace owner. A machine's owner decides whether their machine accepts runner parts from a workspace, since a shared machine would otherwise run code a teammate chose.

Audit

bb is multi-user, and once the product is plugins, most of what happens in a workspace is some plugin acting for some person. Being able to see who did what, and through which plugin, has to be part of the kernel and not a feature added later. The design makes this cheap, because everything already goes through one place.

Every call carries its whole origin. Today a request has an actor (a user, or the user a machine acts for). In the proposal the caller is a chain, and each plugin that makes a call on someone's behalf is added to it:

{
  user: "usr_maya",                       // the person it is done for
  door: "agent",                          // app | cli | agent | http | timer
  thread: "thr_9f2k",                     // the agent session that asked, if any
  via: ["tasks"],                         // plugins the call passed through, in order
}

The kernel writes one record per operation that changes something. A contract marks each operation as a read or a write. Writes are always recorded; reads can be turned on per operation.

WhenOperationWhoThroughHooks that actedOutcome

What makes this more than a request log:

  • Hooks are named. When a hook rewrites an input or answers in the owner's place, the record says which plugin did it. "Why did my push not go through?" has an answer that names a plugin.
  • Agents are told apart from people. Today an agent's bb call is attributed to the user who last wrote in that thread. The record keeps both: it was Maya's agent, in this thread, and not Maya at a keyboard.
  • Plugin changes are operations too. Install, enable, disable, reload and every settings change go through the kernel, so they appear with the person who made them.
  • Secrets stay out. A contract marks fields as secret, and the record keeps their presence but not their value.
  • Plugins can read the log but not edit it. The kernel emits each record as an event, so a plugin can forward it to an outside system. Nothing can hook the write itself. An audit plugin provides the screen and bb audit; owners see everything, members see their own actions.

The honest limit. The log covers what goes through operations. A plugin that calls node:fs or fetch directly leaves no record. Three steps close the gap, in increasing cost: give plugins bb.fs, bb.http and bb.process that are recorded (Claude Code mods can reach the outside only this way, which is why it can list what a mod does); have bb plugin validate flag any direct use of Node built-ins and show it at install; and, for a real guarantee, run third-party plugins in their own process where those built-ins are not available. That last step is the same work as isolation, so wanting audit to be trustworthy is a reason to do isolation earlier than I first suggested.

Failure

  • A hook that only watches fails open. If it throws or runs past its time limit, it is skipped, logged, and the plugin is marked degraded.
  • A hook that guards fails closed. It says so with .failClosed(), and a crash refuses the operation. Hermes does this per hook (pre_tool_call blocks on timeout, the others do not); Claude Code does it with a .catch handler.
  • Unload is one path. Unload, failed load and reload all reverse the plugin's registrations through the loader's record, and a pick-one slot goes back to whatever the plugin displaced. A bb object from an unloaded plugin throws when used, as in Pi and the original bb.
  • Reload says what changed. Hooks and commands are live at once; tools and instructions reach a provider only on its next session. Hermes prints this as an "activation summary", and bb should too.

The code gets harder to follow"What happens on send" is one file today. With hooks it is a chain assembled at run time.bb plugin inspect threads.send prints the chain in order. Hooks go only at named seams, never inside the engine's transaction.

What I would not do:

  • Not make the kernel's own parts replaceable. DeepSeek lets you swap the loader and plugin manager. That is the least useful flexibility and the hardest to keep working.
  • Not build a second UI system. No element trees, no terminal surface. React and data contributions.
  • Not copy any reference's API surface. Their events are about model requests and tool calls. bb's are about threads, machines and people.
  • Not design the engine to be swapped. It should be a plugin in form, using only the public API. Whether anyone could write a different one is not a goal.

15Decisions for you

These are the choices that shape the rest. My recommendation is first in each.

1. How literally "everything"?

Recommended: everything is a plugin in form (it loads through the kernel and uses only the public API), and the leaves are designed to be swapped: providers, environments, sign-in, sidebar, renderers.

The alternatives are to keep the thread engine in core (less work, but core keeps a private door and the API stays second class), or to make every plugin replaceable (DeepSeek's position, and a much larger surface to keep stable).

2. One hook shape, or a result type per event?

Recommended: (e, next) middleware everywhere, as in Claude Code, with each contract stating what a hook may do. It is one thing to learn, and "run something after" needs no second event.

The alternative is Pi's and Hermes's style, where each event has its own result type ({block}, {transform}). It is easier to read for simple cases, and it is how both ended up with 40 or more event names.

3. Should third-party code run on machines?

Recommended: yes, since providers and environments cannot be plugins otherwise; first-party runner parts only at first, and a machine's owner approves each workspace whose runner parts it will run.

This interacts with the multi-user work: on a shared machine, a workspace owner's plugin would run under the machine owner's account.

4. How should core plugins share a database?

Recommended: tables in the shared file, owned by one plugin each, with published read-only tables or views that others may join.

The alternative is strict isolation (a file per plugin, reads only through operations). It is cleaner and would make the thread list, which joins five tables today, much slower or much more complicated.

5. React only, or a UI description that works elsewhere too?

Recommended: React for views, plain data for commands, menus, badges, forms and questions. Revisit if a native mobile app or a terminal UI becomes real.

6. In-process, or a process per plugin?

Recommended: in-process now. Keep everything that crosses an operation serializable, so that isolation can later be a setting, as it is in Hermes.

7. How strong should the audit guarantee be?

Recommended: from step 1, record every write operation with its full caller chain and the hooks that acted on it; give plugins recorded bb.fs, bb.http and bb.process; flag direct use of Node built-ins at install. Treat it as complete only for plugins that run in a separate process.

If "a third-party plugin cannot act without a record" is a requirement and not a goal, decision 6 changes: third-party server and runner parts would run out of process from the start, and only first-party plugins stay in-process.

8. Should plugins written for the original bb keep working?

Recommended: no source compatibility. The factory shape stays close enough ((bb) => …, definePluginApp-like app entry) that porting is mechanical, and step 1's compatibility layer could be kept for the server half if your own plugins need it.

9. Per-person plugins?

Recommended: give settings and storage a scope (workspace, user, project) from the start, and leave "a member installs an app-only plugin just for themselves" until after step 5.
